Defending Home4Paws

A straight answer for every question in your list, grounded in what's actually in the repo — Spring Boot monolith, Supabase-issued JWTs, Postgres, Redis-backed SSE chat, Razorpay. Where your list asks about Kafka, RAG, or voice pipelines, the honest answer is "not in this project" — said plainly, with the reasoning an interviewer is actually testing for.

01 Project understanding & architecture

Qs 1–20

1–5 The pitch: problem, why, users, features

What it is: Home4Paws is a single Spring Boot + React application that merges two things people otherwise solve with three different apps: free pet adoption from NGOs/shelters, paid pet sales from individual sellers, and a pet-supplies store — with a chat channel wired directly into each adoption request so the adopter and the shelter can actually talk before a pet changes hands.

Problem it solves: adoption listings, marketplace sales, and supply shopping are normally fragmented across Instagram DMs, classifieds, and separate storefronts, with no structured way to track a request from "interested" to "approved" to "picked up," and no record of the conversation. Home4Paws puts the listing, the request workflow, the chat, and the payment (for sales/supplies) behind one auth model and one data model.

Why built: it's a portfolio/learning project that deliberately covers a full production slice — real third-party auth (Supabase), real payments (Razorpay), real-time messaging (SSE + Redis pub/sub), and a real deploy pipeline (Docker Compose behind Nginx/Certbot on EC2) — rather than a CRUD toy.

Users: four roles drive the whole app — NORMAL_USER (browses, adopts, buys supplies), SELLER (lists pets for sale), NGO_SHELTER (lists pets for free adoption), ADMIN (verification, moderation, platform stats).

Major features: dual pet listings (adoption vs. marketplace) on one Pet entity, an adoption-request approve/reject workflow, live per-request chat, a product catalog with cart and Razorpay checkout, order history, and an admin dashboard.

6, 12–13 Walk the architecture / draw it / what happens on a request

It's a classic three-tier monolith, not microservices:

React SPA (Vite)→ Axios + Supabase JWT→ Nginx (TLS, reverse proxy)→ Spring Boot (JwtFilter → Controller → Service → Repository)→ Postgres (Supabase)

Two components sit beside that main line: Redis, used both as a Spring cache and as the pub/sub backbone for chat fan-out across app instances; and Razorpay, called out-of-band by the backend during checkout/subscription to create an order, then hit again by the frontend's Razorpay checkout widget, then verified server-side via HMAC signature.

On a normal request: browser sends the request with Authorization: Bearer <supabase-jwt> → Nginx terminates TLS and proxies to the Spring container → JwtFilter (a OncePerRequestFilter) validates the token via JwtUtil, loads the local User through CustomUserDetailsService, and populates the SecurityContext → Spring Security's method-level @PreAuthorize checks the role → the controller delegates to a service → the service uses a Spring Data JPA repository → Hibernate issues SQL to Postgres → the entity is mapped back to a DTO/JSON and returned through the same chain.

7–11, 14–20 Why this shape, components, bottlenecks, limitations, redesign

Why a monolith, not microservices (7–8): one team, one deploy target, and a data model where almost every feature (pets, requests, chat, orders) reads and writes the same handful of tightly related tables. Microservices would mean distributed transactions across "Pet service" and "Request service" for something that's one @Transactional method today — pure overhead at this scale, and it's the answer I'd give and defend, not a limitation I'd apologize for.

Components and responsibilities (9–11): controller = HTTP boundary + input shape; service = business rules and transactions; repository = persistence; config = cross-cutting (security, CORS, Redis, chat pub/sub); frontend pages = route-level screens, context/CartContext = client cart state, api/axiosConfig = attaches the Supabase token to every call. They communicate in-process (Java method calls) on the backend, and over REST/SSE between frontend and backend — there's no inter-service RPC because there's only one backend service.

Critical path / bottleneck / SPOF (15–17): the critical path for the whole app is JwtFilter → Postgres — every authenticated request pays for a JWT validation and at least one DB round trip, and Postgres (a single Supabase instance, no replicas configured) is both the bottleneck under write load and the single point of failure: if it's down, every feature except static pet/product browsing (if cached) stops. Redis is a soft SPOF — chat breaks without it, but the CRUD paths still work since it's not on the auth path.

Assumptions (18): trusted, low-tampering client (JWT trust model assumes Supabase's signature is enough — no separate password check); moderate concurrent load (single Postgres instance, no read replicas, no sharding); images/files aren't stored by the app itself (imageUrl fields imply an external host or Supabase storage, not local disk).

Biggest limitations / what I'd change today (19–20): real the plaintext DB credentials and Razorpay keys committed in application.properties/docker-compose.yml — first thing I'd fix, move to environment variables + a secrets manager. Second: no read replica or connection pooling tuning documented, and ddl-auto=none means schema changes are manual, not tracked by a migration tool (no Flyway/Liquibase) — I'd add one. Third: the stale README undersells the current feature set, which is a documentation debt, not an architecture one.

02 Why this technology

Qs 21–44 — answered as "what we used" vs. "what the list asks about that we didn't use"

21–23, 25–31, 38–40 Java, Spring Boot, REST, sync, monolith, JPA used

Java + Spring Boot: strong typing catches request/entity mismatches at compile time, Spring Data JPA removes CRUD boilerplate, Spring Security's method-level @PreAuthorize maps cleanly onto a 4-role system, and the ecosystem (Spring Cache, Spring Data Redis) covers everything the project needed without extra glue code.

Why not Node.js/Python (23–24): both would work fine for this feature set; the real reason is I wanted statically-typed domain modeling for the role/permission matrix (four roles × five resource types) where a typo'd string role is a runtime bug in a dynamically typed stack and a compile error in Java.

REST, not GraphQL (25–26): the frontend's data needs per page are simple and don't suffer from REST over/under-fetching (a pets list, a pet detail, a cart) — GraphQL's flexible querying would be solving a problem this app doesn't have, at the cost of a query-planning/N+1 layer to build and secure.

HTTP, synchronous (27–29): requests are simple create/read/update operations with an immediate expected response (add to cart, approve a request); nothing in the flow genuinely benefits from fire-and-forget except chat, which is why chat specifically uses SSE (a long-lived async push channel) instead of polling — the rest of the app didn't need gRPC's binary framing or an async message bus.

Monolith over microservices (30–31): see 7–8 above — one deploy unit, one Postgres schema, no team-boundary reason to split.

JPA/Hibernate over raw JDBC (38–40): the entity graph (User↔Pet↔AdoptionRequest↔ChatMessage↔Order↔OrderItem) has enough relationships that hand-writing JDBC mapping code for each would be pure repetition; JPA's repository interfaces also make the role-scoped queries (e.g. "pets owned by this shelter") declarative.

32, 34–37, 41–44 Redis, Postgres, ORM, cloud, Docker used

Redis: two jobs — Spring Cache for read-heavy, rarely-changing data, and pub/sub as the fan-out mechanism so chat messages reach every app instance's SSE connections, not just the instance that received the POST.

Postgres, SQL not NoSQL (34–36): the data is inherently relational — a pet belongs to a shelter/seller, has many adoption requests, a request has many chat messages, an order has many order items — and the app needs transactional guarantees around checkout (order + order items + stock decrement must succeed or fail together). A document store would mean denormalizing this graph or doing manual joins in app code for no benefit.

Supabase as the Postgres host (37): managed Postgres plus a built-in auth product in one, which is also why auth ended up as a JWT-trust model instead of home-grown sessions — see Section 5.

Docker (42): reproducible builds and the ability to run backend, frontend, Redis, and Nginx as one docker-compose unit on the EC2 box, so "it works on my machine" doesn't become a deploy-day problem.

Kubernetes (43): not used — a single EC2 instance running docker-compose is the right size for this traffic; K8s would add an orchestration layer with nothing to orchestrate (one replica per service). I'd reach for it the moment I needed multiple backend instances behind a load balancer with rolling deploys, not before.

33 Kafka not used

No message broker in this project — every write is synchronous and immediately consistent (place an adoption request, approve it, send a chat message), and the one place that could look async — chat fan-out — is solved at a scale where Redis pub/sub is enough: single-digit backend instances, not a multi-region fleet needing durable, replayable event streams. I'd reach for Kafka if the app grew an event-driven side — e.g. "notify all interested users when a new pet matching their saved search is listed" — where you want durable, replayable, multi-consumer fan-out rather than a direct call.

03 Database design

Qs 45–74

46–51 Schema shape and normalization

Core tables: users (role, email, Supabase-linked identity), pets (species, breed, age, price nullable, status, gender, city/state, FK to owner), products (category, type, price, stock, imageUrl), orders + order_items (Razorpay order/payment IDs, status), adoption_requests (adopter FK, pet FK, status), chat_messages (request FK, sender, body, timestamp), subscriptions.

It's normalized to 3NF for the transactional core — order_items is split out from orders specifically so an order can hold N products without repeating order-level fields per line item, and pets doesn't duplicate owner info (name, contact) that lives on users — it's joined via FK. The one deliberate "denormalization" is that Pet.price is nullable and reused for both adoption (null) and marketplace (set) listings rather than splitting into two tables — a single filterable listings table matters more than schema purity here, since both listing types share every other column and the UI, and a query like "all pets in Mumbai" would otherwise need a UNION across two tables.

52–65 Keys, indexes, query cost, scale

Primary keysJPA-managed auto-increment/identity IDs per entity — simple, sequential, and sufficient since IDs aren't exposed as guessable security boundaries (auth is role-based, not ID-obscurity-based).
UUID vs auto-increment (53)Auto-increment was the pragmatic default for a single-database app with no multi-region write conflicts to avoid; I'd switch to UUIDs if this ever became multi-instance-writable or the IDs needed to be unguessable in a public URL.

Indexes (54–58): not explicit in the current schema beyond primary/foreign keys — this is the honest gap I'd name if asked directly. The ones I'd add first: pets(status, city) for the adoption/marketplace browse filters, adoption_requests(pet_id, status) for the shelter's request queue, and orders(user_id) for order history — all three are the actual WHERE clauses the controllers issue. Downside of indexes: slower writes (every insert/update also touches the index), more storage, and a "why is this insert slow" surprise if you over-index a write-heavy table.

100M rows / partitioning (59–61): at that scale I'd first check whether it's actually one hot table (likely chat_messages, which grows unboundedly per request) — partition that by date range or by adoption_request_id hash, add read replicas for the browse-heavy pets/products queries, and archive completed/old orders out of the hot table.

Investigating a slow query (62–65): run EXPLAIN ANALYZE, check whether it's doing a sequential scan where an index should be hit, check join order and whether the ORM is issuing N+1 queries (a classic JPA trap — e.g. fetching an order and lazily loading each order item in a loop instead of one JOIN FETCH).

66–74 Concurrency, transactions, consistency

Concurrent updates (66–69): the highest-risk case is two adopters requesting the same pet, or an admin deleting a pet while a request is being approved. Spring's default transaction isolation (Postgres READ COMMITTED) is what's in effect — good enough for this workload since conflicting writes are rare and not financial; I did not add explicit optimistic locking (@Version), which is the honest next step for the Pet.status field specifically, so "approve" can't race against "pet already adopted."

Transactions (70–74): the checkout flow is the clearest case — OrderService.checkout must create the Order and all its OrderItem rows atomically; if the app crashed mid-way you'd want either both rows or neither, which is what @Transactional (Spring's declarative transaction boundary, rolling back on unhandled exceptions) gives you. The Razorpay call itself happens before commit and returns an order ID that's stored — if the DB write then failed, you'd have an orphaned Razorpay order with no local record, which is the actual failure mode I'd harden next (compensating cleanup or moving the Razorpay call to a step verified after commit).

04 API design

Qs 75–96

Verbs, validation, errors, versioning

Verb choices (77–78): POST for creating a pet listing, an adoption request, or a chat message (resource creation, non-idempotent); DELETE for admin pet/user removal; no PUT/PATCH distinction is heavily exercised in this app since most "updates" are really status transitions (approve/reject a request, mark an order paid) modeled as dedicated endpoints rather than generic resource replacement — that's a REST-purity tradeoff I made for clarity over strict verb semantics.

Validation (80–84): request DTOs (RegisterRequest, CheckoutRequest, LoginRequest) shape what the controller accepts at the boundary; a GlobalExceptionHandler (@ControllerAdvice) catches exceptions centrally and returns a consistent ErrorResponse body with an appropriate HTTP status, instead of leaking stack traces or letting each controller hand-roll error JSON.

Idempotency (88–91): the one place this actually matters is Razorpay's payment verification callback — /api/orders/verify checks the order isn't already PAID before flipping status, so a retried webhook/client call can't double-process a payment. Most other endpoints (list pets, view chat) are naturally idempotent as GETs.

Versioning / backward compatibility (85–87): not versioned today — frontend and backend deploy together from the same repo via one CI/CD pipeline, so there's no independent-client compatibility problem to solve yet. I'd introduce /api/v2/... the moment a mobile client or third-party integration needed the old contract to keep working.

Downstream failure (95–96): the one real downstream dependency is Razorpay. If it's unavailable, checkout fails fast with an error surfaced to the user rather than silently retrying — there's no circuit breaker today, which is a gap I'd close with a library like Resilience4j if this saw production payment volume.

05 Authentication & security

Qs 97–118 — this is the section most worth over-preparing; it's the project's most distinctive design decision

97–104 The JWT-trust model, explained precisely

Home4Paws does not do local password authentication. Supabase Auth owns sign-up/sign-in (email+password and Google OAuth) and issues a signed JWT. The frontend sends that JWT as Authorization: Bearer <token> on every API call (via axiosConfig.js). On first contact, the frontend calls POST /api/auth/sync, and AuthService.syncUser validates the token, then finds-or-creates a matching local User row keyed by email, defaulting role to NORMAL_USER unless a valid role string was supplied (needed specifically for OAuth signups, since Supabase doesn't propagate custom user_metadata through the OAuth redirect). Every subsequent request runs through JwtFilter, a OncePerRequestFilter that validates the token via JwtUtil, loads the local user through CustomUserDetailsService, and populates Spring Security's SecurityContext — so @PreAuthorize("hasRole(...)") works exactly like it would with local sessions, just backed by a token Supabase issued.

Because Spring's UserDetails still requires a getPassword(), the local User entity returns an empty string — password verification never happens in this backend; trust is entirely delegated to Supabase's signature. JwtFilter also accepts the token as a ?token= query param specifically for the SSE chat endpoint, since EventSource can't set custom headers.

98–99, 101–106 Why JWT, token storage, refresh, revocation, RBAC

Why JWT over server sessions (98–99): it wasn't really a from-scratch choice — Supabase Auth's product is JWT-based, so once I chose Supabase for OAuth + email/password, JWT was the natural fit for a stateless Spring backend (no server-side session store needed, works cleanly with CORS across the SPA's own origin).

Refresh/revocation (102–104): handled by the Supabase client SDK on the frontend, not by this backend — Supabase manages refresh-token rotation and expiry. If a refresh token were stolen, that's a Supabase-side session-revocation action; the backend's own exposure is limited to however long an already-issued access token stays valid, since JwtFilter doesn't check a local blocklist.

RBAC (105, 107): Role enum (NORMAL_USER, SELLER, NGO_SHELTER, ADMIN) maps to a Spring Security authority (ROLE_<role>); endpoints are gated with method-level @PreAuthorize("hasRole('...')") — e.g. pet creation/deletion restricted to NGO_SHELTER/SELLER, product catalog writes to ADMIN, adoption-request creation to NORMAL_USER, and the entire AdminController is class-level gated to ADMIN.

109–118 Injection, XSS, CSRF, secrets

SQL injection (109): JPA/Hibernate parameterizes all queries by default (no raw string-concatenated SQL in the services), which closes this off structurally rather than by discipline.

XSS (110): React escapes rendered content by default; the app doesn't use dangerouslySetInnerHTML for user-generated content like chat messages or pet descriptions, so injected markup renders as text, not HTML.

CSRF (111): CSRF protection is explicitly disabled in SecurityConfig — safe here specifically because the API is stateless and bearer-token-authenticated rather than cookie-session-authenticated; CSRF exploits rely on the browser auto-attaching cookies, which doesn't apply when auth is a header the attacker's page can't set cross-origin.

Real gap, said straightPasswords/DB credentials aren't the concern here since there's no local password store — but application.properties and docker-compose.yml do have a hardcoded Supabase Postgres password and default Razorpay test keys committed to git history (114–117). That's the answer I give directly if asked "are secrets in git" — yes, and here's exactly how I'd fix it: move to environment variables injected at deploy time (already partially staged via the GitHub Actions SSH deploy), rotate the exposed credentials, and add a pre-commit secret scanner.

06 Scalability

Qs 119–140

Honest current scale, and the actual first bottleneck

Current scale (119–120): this is a single-EC2-instance, single-Postgres-instance deployment — it's sized for a portfolio/early-stage load, not measured production throughput. The honest answer under pressure: "I haven't load-tested it; here's what I'd expect to break first and why," which is a stronger answer than inventing a number.

First bottleneck at 10× (121–123): Postgres write contention on pets/orders during peak browse+checkout, followed by the single backend container's thread pool under concurrent SSE chat connections (each open chat is a held connection).

Statelessness (128–130): the backend is stateless by design — no server-side session, auth is a bearer token validated per-request — so horizontal scaling (129, 125–127) is straightforward: put 2+ backend containers behind Nginx/a load balancer, and any instance can serve any request. If one crashes, in-flight requests fail over on retry with no session to lose (130) — the one exception is a live SSE chat connection, which would drop and need the client to reconnect.

Scaling the database (131–140): read replicas first (pets/products browsing is read-heavy and doesn't need read-your-writes consistency), sharding only if a single table's write volume genuinely outgrows one primary — not a near-term need here. Caching (138–140): I'd cache the product catalog and public pet listings (read-heavy, low write frequency) in Redis with a short TTL, invalidated on write; I would not cache order history or chat (per-user, must be fresh). If Redis goes down, the app should degrade to hitting Postgres directly for those reads rather than hard-failing — that's a resilience gap worth naming (currently Spring Cache would just throw if Redis is unreachable, unless configured with a fallback).

07 Caching / Redis

Qs 141–158

What's cached, strategy, failure mode

Why Redis over in-process cache (141, 144): the app is meant to run multiple backend instances behind a load balancer eventually — an in-memory (e.g. Caffeine) cache would be per-instance and inconsistent across replicas; Redis gives one shared cache all instances agree on, and doubles as the pub/sub layer chat already needs, so it's not a second piece of infrastructure.

What's cached and why (142–143): Spring Cache is wired for read-heavy, low-churn lookups — pet/product listings are the natural candidates (many reads per write); user-specific data (cart, orders, chat) is intentionally not cached, since staleness there is a correctness bug, not a minor inconvenience.

Strategy (145–151): cache-aside (read from cache, fall through to DB and populate on miss) fits this app better than write-through, since writes (adding a pet) are far less frequent than reads (browsing), so paying the invalidation cost only on the rare write is cheaper than updating the cache on every write regardless of whether it's ever read again.

Chat's actual use of Redis (156–158): distinct from the cache — ChatPubSubConfig/ChatSseManager use Redis pub/sub so a chat message sent to one backend instance is broadcast to the SSE connections held by every instance. If Redis goes down, chat delivery breaks (messages can still be persisted to Postgres and fetched via GET /api/chat/{requestId} on reconnect, but live push stops) — the rest of the app (pets, products, orders) keeps working since Redis isn't on their path.

Stampede/penetration/avalanche (152–155): not explicitly guarded against today (no lock-on-miss, no negative caching for misses) — at this traffic level it hasn't mattered, but the fix for stampede is a short-lived mutex or "probabilistic early recompute" around the cache-population step, and for penetration, caching negative results with a short TTL.

08 Kafka / message queues

Qs 159–185 — not part of this project

The honest no, and the conceptual answer behind it

Home4Paws has no message broker. Every write path is synchronous request/response, and the one feature that looks "event-like" — chat — is solved with Redis pub/sub, which is the right-sized tool for fanning a message out to a handful of app instances, not for durable, replayable, multi-consumer event streams.

If pressed on Kafka concepts generally: a topic is a named stream of events; a partition splits a topic for parallel consumption, ordered only within a partition; the partition key determines which partition a message lands in (same key → same partition → preserved order for that key); a consumer group lets multiple consumers split a topic's partitions for parallel processing, each partition owned by one consumer in the group at a time; delivery guarantees range from at-most-once (fire and forget) through at-least-once (default, requires idempotent consumers to handle duplicates) to exactly-once (transactional producers/consumers, higher overhead). I'd reach for Kafka in this project the moment I needed durable, replayable events — e.g. "email every user with a saved search when a matching pet is listed," which benefits from decoupling the pet-listing write from a potentially slow/failing notification fan-out.

09 Concurrency & multithreading

Qs 186–204

Where the JVM's thread model actually shows up

Spring's embedded Tomcat handles concurrency for free — every HTTP request runs on its own thread from the servlet container's thread pool, so the app doesn't hand-manage threads for normal request handling. The places concurrency is genuinely relevant: SSE chat connections (each open chat stream holds a thread/connection for its duration — this is the actual scaling limit on concurrent chats per instance, not raw CPU), and the potential race on Pet.status if two adopters' requests are approved near-simultaneously (see Q66–69) — that's the one spot I'd add either a DB-level unique constraint/optimistic lock (@Version) or a synchronized/transactional guard rather than trusting request ordering.

I did not hand-roll thread pools, ExecutorServices, or explicit locks in this codebase — it leans on Spring/Tomcat's managed concurrency and the database's own transaction isolation rather than reinventing thread safety at the application layer, which is the right call for this feature set (no CPU-bound background jobs, no manual batching).

10 Failure handling

Qs 205–224

Dependency downWhat actually happens todayWhat I'd add
PostgresEvery DB-backed endpoint fails with a 500 via GlobalExceptionHandlerHealth check + auto-restart; eventually a replica for read failover
RedisCached reads fall through to an exception unless a fallback is configured; chat push stopsGraceful cache-miss fallback to DB; chat auto-reconnect with backoff on the client
RazorpayCheckout call fails, order stays PENDING, user sees an errorRetry with exponential backoff + jitter for transient errors only (not for 4xx); a circuit breaker so repeated Razorpay outages fail fast instead of piling up slow requests

Retries, when not to (211–216): retry idempotent, transient failures (network blip calling Razorpay to create an order) — never retry a payment verification that already returned a definitive "invalid signature," since that's not transient, it's wrong. Exponential backoff spaces retries out so a struggling dependency isn't hammered harder by retries; jitter (randomizing the delay slightly) prevents many clients from retrying in lockstep and re-creating the exact spike that caused the failure.

Circuit breaker (217–221): not implemented today — the honest gap. If it were: the circuit opens after N consecutive Razorpay failures, short-circuits further calls (fail fast instead of timing out slowly), and half-opens after a cooldown to test if the dependency recovered.

Mid-operation crash (222–224): the checkout transaction (Order + OrderItems) is wrapped so a crash before commit loses nothing (nothing was ever durably written) — the actual risk is the reverse ordering: if the Razorpay order is created successfully but the local commit fails afterward, you get an orphaned Razorpay order with no local record. I'd fix this by confirming the DB write succeeded before treating the Razorpay order as "real," or reconciling via Razorpay's webhook as the source of truth.

11 "Design it for 10 million users"

Qs 225–243

I would not start by splitting into microservices — that's the tempting wrong answer. I'd scale the monolith horizontally first: multiple stateless backend containers behind a load balancer (cheap, since auth is already stateless), Postgres read replicas for the browse-heavy pet/product queries, Redis caching pushed harder on those same read paths with sensible TTLs, and CDN/static hosting for the frontend build instead of serving it through the same Nginx as the API.

I'd only consider splitting a service out — chat is the clear first candidate, since it has a genuinely different scaling shape (long-lived connections vs. short request/response) — once the monolith's chat traffic specifically became the bottleneck, not preemptively. Distributed transactions (233) only become a problem if I split services that share a transaction boundary today (order + order items) — which is exactly why I wouldn't split payments out on day one.

Deployment at that scale (236–241): replace the current single-EC2 SSH-deploy pipeline with rolling/blue-green deploys behind the load balancer (deploy the new version to half the fleet, health-check, shift traffic, repeat) so a bad deploy is a fast rollback, not downtime. SLA/latency/throughput targets (241–243) would be defined from real measured baselines first — I wouldn't quote a number I haven't tested.

12 AI / LLM

Qs 244–270 — not part of this project

Home4Paws has no LLM integration — no generation, no prompt pipeline, no model calls anywhere in the codebase. If this is being asked because the role is an AI-engineering role, the honest framing is: "this project demonstrates the backend fundamentals an LLM feature would sit on top of — auth, transactional data, caching, real-time delivery via SSE (the same pattern you'd use to stream LLM tokens to a client) — but it doesn't include a model integration." I'd rather say that plainly than stretch the project to claim something it doesn't do.

14 Voice AI / calling

Qs 297–320 — not part of this project

No telephony or voice pipeline here. The closest analog in this codebase is the chat feature's real-time delivery mechanism — SSE over a persistent connection, fanned out via Redis pub/sub across instances — which is conceptually the same "keep a channel open and push low-latency updates" problem a voice pipeline solves for audio frames instead of text messages, just at a much smaller latency budget.

15 Observability

Qs 321–334

Current state: RequestLoggingFilter and logback-spring.xml give structured request logging to logs/home4paws.log — that's the extent of it; there's no metrics/tracing stack (no Prometheus/Grafana, no distributed tracing) wired up yet, which is the honest gap I'd name rather than overstate.

What I'd add first (322, 329–334): request-level metrics (latency, status code, per-endpoint throughput) via Micrometer → Prometheus, since "which API is slow" and "is the error rate spiking" are the two questions logs alone answer slowly. Database: Postgres's own pg_stat_statements for query-level timing. Redis: hit/miss ratio on the cache, connection count on pub/sub. Alerting I'd configure: error-rate spike on checkout/payment-verify specifically (money-path), and Postgres connection pool exhaustion.

Logs vs metrics vs traces (324): logs are discrete events with full context (good for "what exactly happened in this one request"); metrics are aggregated numbers over time (good for "is the system healthy right now"); traces follow one request across components (this app doesn't need distributed tracing yet since it's one backend process — it becomes essential the moment there's more than one service to cross).

16 Testing

Qs 335–349

A src/test/java tree exists in the standard Spring Boot layout. The honest, defensible answer if pressed on coverage depth: I'd describe what should be tested at each layer rather than overclaim — unit tests around service-layer business rules (role checks, order total calculation, adoption-status transitions) with repositories mocked; integration tests (@SpringBootTest + an embedded/test Postgres or Testcontainers) around the full checkout flow, since that's the path with real money and real transactional risk; and a mocked Razorpay client for testing signature verification logic without hitting the real API.

Load testing (345–348): not performed — I'd use k6 or JMeter against the checkout and pet-browse endpoints specifically, since those are the two paths most likely to matter first (read-heavy browse, write-heavy + external-dependency checkout).

17 Deployment / DevOps

Qs 350–363

push to main→ GitHub Actions: build backend (Maven) + frontend (npm)→ SSH into EC2→ git reset --hard→ docker compose build→ docker compose up -d

18 The "why → why not" drill, worked example

Qs on the recurring depth pattern — worked through with the project's real Redis usage, exactly as the list's own Redis example does

Why Redis? Shared cache across future multiple backend instances, plus it's the pub/sub layer chat needs anyway — one dependency, two jobs.

Why not a local in-memory cache? Per-instance caches go inconsistent the moment there's more than one backend container, which is the direction this app's scaling plan already points.

What did you cache? Read-heavy, low-churn data — pet and product listings. Not cart, orders, or chat — those must always be fresh per user.

Why was that data cacheable? High read-to-write ratio (many browsers, few new listings per hour) and tolerance for a few seconds of staleness on a browse page.

What TTL, why? Short (minutes, not hours) — long enough to absorb repeated browse traffic, short enough that a newly listed pet shows up without a manual cache-bust.

How do you invalidate it? Cache-aside with invalidation on write — when a pet/product is added or removed, evict the relevant cache key rather than waiting out the TTL.

What happens if Redis goes down? Today: cached reads throw unless a fallback is configured, and chat push stops. Should be: fall through to Postgres for reads, degrade chat to poll-on-reconnect.

Stampede? Not guarded today — the fix is a short lock/mutex around cache population so one miss doesn't become N simultaneous DB hits.

How would you scale Redis? Redis Cluster or a managed Redis with replicas, once either cache volume or pub/sub fan-out (concurrent chats) outgrew one instance.

The pattern to reuse on any other component: what → why → alternative rejected and why → tradeoff accepted → failure mode → behavior at 10× → the one thing you'd change first. Run this same six-step chain for JWT auth, the checkout transaction, and the monolith-vs-microservices call — those are the three most likely to get drilled.

20 The twenty dangerous ones

One-line answers, ready to expand from any section above

  • Architecture: stateless Spring Boot monolith — one team, one schema, no split boundary yet.
  • Database: Postgres — the data is relational and checkout needs real transactions.
  • Why not X: every alternative considered (Mongo, GraphQL, Kafka, microservices, Kubernetes) solves a scaling or flexibility problem this app doesn't have yet.
  • DB down: every DB-backed endpoint fails with a handled 500 — no replica failover configured yet.
  • 100× traffic: horizontal backend scaling first (already stateless), then Postgres read replicas, then harder caching.
  • Biggest bottleneck: single Postgres instance under write load.
  • How to scale: load balancer + N stateless backend containers + read replicas + Redis caching on browse paths.
  • Concurrent same-data edit: real gap — no optimistic locking on Pet.status yet; READ COMMITTED isolation only.
  • Failure handling: centralized GlobalExceptionHandler; no circuit breaker yet on Razorpay calls.
  • Retries: only for transient, idempotent calls (Razorpay order creation) — never retry a definitive verification failure.
  • Duplicate requests: payment verification checks status before transitioning — the one place it's actually needed.
  • Consistency: @Transactional around checkout; the Razorpay-order-vs-DB-commit ordering is the one known weak spot.
  • Caching: pet/product listings, cache-aside, short TTL, invalidated on write.
  • Kafka: not used — no event-driven feature exists yet to justify it.
  • Sync vs async: synchronous REST everywhere except chat, which is push-based SSE for a genuinely real-time need.
  • Redesign for production: migrations tool (Flyway), secrets out of the repo, optimistic locking on Pet.status, a circuit breaker on Razorpay, blue-green deploys.
  • Weakest part: the committed plaintext credentials — said plainly, not hidden.
  • Hardest problem solved: the Google OAuth role bug (Section 19) — silent, architecture-specific, non-obvious.
  • A decision you'd revisit: not adding a migration tool from day one — ddl-auto=none with manual schema changes doesn't scale past a solo project.
  • One week to improve it: secrets to env vars + rotate keys, add Flyway, add optimistic locking on Pet.status, add indexes on the actual hot WHERE clauses.
