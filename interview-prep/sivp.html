Defending SIVP

A straight answer for every question in the list, grounded in what's actually in the repo — a React SPA talking directly to Supabase (Postgres + Auth + Storage + Realtime) for everything CRUD, and a thin stateless Spring Boot bridge that forwards idea-validation requests to a 10-agent n8n pipeline running on Gemini. Where the list asks about Kafka, Redis, microservices, RAG, or voice pipelines, the honest answer is "not in this project" — said plainly, with the reasoning an interviewer is actually testing for.

01 Project understanding & architecture

Qs 1–21

2–6 The pitch: problem, why, users, features

What it is: SIVP (Startup Idea Validation Platform) is a startup-idea validation engine bolted onto a full incubator-management app. A founder submits a 7-field idea form; ten specialized AI agents (VisionAI, MarketMind, RivalScope, BuildIQ, SWOTify, GrowthIQ, FundIQ, MentorAI, IncubaTrack, ReportForge), orchestrated by a parent workflow I call NEXUS, run against it and return a single structured report — PMF score, TAM/SAM/SOM, competitor gaps, SWOT, financial forecasts, and a weighted Investor Readiness Score — exportable as PDF/DOCX/PPTX. Around that engine sits an incubator platform: role-based dashboards for founders, mentors, and admins, cohorts, mentor assignment, document requests, a funding leaderboard, and live community chat.

Problem it solves: first-time founders build for months on a hunch because market research and competitor analysis are either expensive (consultants) or scattered across a dozen tools; incubators separately run their cohort through email and spreadsheets with no structured evaluation record and no visibility into who's stuck.

Why built: to make validation not a one-off PDF but a first-class part of the same system that runs a founder's actual incubator journey — from "just an idea" to mentor assignment, milestones, documents, and funding tracking.

Users: three roles enforced at the database level, not just the UI — student/founder (submits ideas, tracks progress), mentor (reviews assigned mentees, evaluates, schedules), admin (manages cohorts, invitations, applications, engagement, funding figures) — plus a public surface (apply, showcase, events, resources, opportunities) that needs no login.

Major features: the 10-agent validation pipeline with investor-readiness scoring; multi-tenant institutions with invite-only elevated roles; teams/co-founders + achievements; community chat via Supabase Realtime; document requests + private storage; a funding leaderboard; government-scheme matching (static + AI-personalized via MentorAI); PDF/DOCX/PPTX export.

7, 13–15 Walk the architecture / draw it / what happens on a request

Three tiers, deliberately split along a different axis than usual — not "frontend / backend / database" in the classic sense, but CRUD (fast, direct) vs. long-running AI orchestration (slow, relayed):

React SPA (Vite)→ Supabase directly (Auth, Postgres+RLS, Storage, Realtime)
React SPA→ Spring Boot (stateless bridge)→ n8n webhook (10 Gemini agents, NEXUS orchestration)→ JSON report back

For every dashboard, chat message, document upload, or leaderboard read, the browser talks straight to Supabase — there is no backend hop, and Postgres Row Level Security is the actual authorization boundary. Only idea validation goes through Spring Boot, because the browser can't call n8n directly (CORS, and n8n shouldn't be a public-CORS target) and because that call needs a much longer timeout than a normal API request.

On a validation request: POST /api/validate with the 7 idea fields → ValidationController → N8nService POSTs to the n8n webhook with a 10s connect / 180s read timeout (the pipeline takes 30–90s) → NEXUS runs VisionAI → {MarketMind, RivalScope, BuildIQ} in parallel → SWOTify (merges those three + VisionAI) → {GrowthIQ, MentorAI} → FundIQ (consumes upstream scores for the weighted Investor Readiness Score) → IncubaTrack → ReportForge → one JSON blob back → Spring Boot returns it verbatim → normalizeReport.js defensively reshapes it (tolerating unresolved {{ }} n8n expressions, trailing-space keys, USD-in-parens) into the flat shape the report UI renders, and best-effort persists it to public.reports if the user is logged in.

8–12, 16–21 Why this shape, components, bottlenecks, limitations, redesign

Why not microservices (8–9): a monolith-per-concern (one Spring service, one BaaS, one workflow engine) matches the real complexity — one team, no independent scaling need between "submit an idea" and "manage a cohort." Splitting further would add network hops and distributed-transaction risk for a system doing maybe a few hundred validations a day.

Components and responsibilities (10–12): ValidationController = HTTP boundary; N8nService = the one integration point, owns the timeout config; ApiExceptionHandler = turns any n8n/RestTemplate failure into a clean 502; on the frontend, lib/store.js = every Supabase query in one place, lib/auth.jsx = session + profile loading, lib/normalizeReport.js = the one place raw pipeline JSON becomes UI-shaped data. They communicate over plain HTTP (frontend↔backend, backend→n8n) and over Supabase's client SDK (frontend↔Postgres) — there's no inter-service RPC because there's exactly one custom backend service.

Critical path / bottleneck / SPOF (16–18): the critical path is the validate flow, because it's synchronous and user-facing for up to 90s. The real-world bottleneck isn't my code at all — it's Gemini's free-tier rate limit (20 req/day, and gemini-2.0-flash specifically has 0 free-tier quota, a documented gotcha). The single point of failure is n8n itself: down or the NEXUS workflow inactive → every validation 502s. Everything else (dashboards, auth, chat, documents) has zero dependency on n8n and keeps working — that isolation was a deliberate design choice, not an accident.

Assumptions (19): validation traffic is low-volume/bursty (a cohort's worth of founders, not concurrent thousands), so a synchronous 90s request is acceptable UX rather than needing an async job queue — explicitly deferred to a later phase in the project's own spec doc.

Biggest limitations / what I'd change (20–21): no job queue for validation — a page refresh mid-run loses the state with no way to resume; the report is normalized entirely client-side, so any n8n schema drift breaks the frontend silently; n8n runs self-hosted on a single EC2 box with no redundancy. First fix: make validation async — POST creates a reports row in pending state immediately, a callback/poll fills it in when n8n finishes, removing the 180s open connection.

02 Why this technology

Qs 22–46 — "what we used" vs. "what the list asks about that we didn't use"

23–30, 40 Java, Spring Boot, REST, sync used

Why Java/Spring Boot, not Node/Python: the backend does exactly one thing — relay JSON with a long timeout. Any of the three would work equally well; Spring's RestTemplate timeout configuration and @RestControllerAdvice exception handling are trivial to get right, and it matched the stack the project committed to for the Java-strength angle. I wouldn't claim Java is objectively better here — a Node/Express version would honestly be a few lines shorter for this one endpoint.

Why REST, not GraphQL/gRPC (27–28): one custom endpoint, plus Supabase's own auto-generated REST (PostgREST) for everything else. GraphQL solves overfetching across many resource shapes — I have neither problem. gRPC's binary framing buys nothing when the payload is inherently JSON (it came from an LLM as JSON) and the client is a browser.

Synchronous, not async (30–31): the validate flow is a single request/response with an immediate expected outcome (submit → wait → report). It's the one place I'd argue for async on a redesign — see Section 10 — but as shipped it's deliberately simple.

32–33, 36–44 Not microservices, Postgres, Docker used

Not microservices: covered in Section 1 — wrong tool for one team and this data/traffic shape.

Postgres via Supabase, not MongoDB (36–39): the data is genuinely relational — founders belong to teams, teams belong to institutions, meetings reference both a student and a mentor, RLS policies join across profiles/teams/team_members constantly. That's exactly what a relational DB with row-level security is built for; MongoDB would mean re-implementing multi-tenant access control in application code instead of getting it enforced at the DB layer for free.

Why Supabase specifically: three things visible directly in the code — Auth (JWT issuance, session refresh, Google OAuth, all via supabase.auth.*), Row Level Security as the actual authorization layer (every table has explicit policies keyed off auth.uid()/my_role()/my_institution(), so even a client with the public anon key can't cross a tenant boundary), and Storage + Realtime (the documents/avatars buckets and the live community chat subscription) out of the box.

Docker (42): reproducible builds and running backend + frontend (nginx) + n8n as one Docker Compose unit on a single host.

Kubernetes (43): not used — one host running Compose is the right size for this traffic; K8s would add an orchestration layer with nothing to orchestrate.

34–35 Redis, Kafka not used

No caching layer exists because nothing here is read-heavy enough to need one — Postgres directly serves dashboard queries at incubator scale (dozens–hundreds of rows per table). No message queue exists because there's no async event pipeline — the one "event" (idea submitted → report ready) is a single synchronous HTTP call. If I introduced Redis: cache-aside in front of the public showcase and leaderboard queries, short TTL, no invalidation needed since a few seconds of staleness there is fine. If I introduced a queue: replace the synchronous n8n call with a validation-requested/validation-completed pair so the frontend polls instead of holding a connection open for 90s — I'd reach for a simple queue (SQS, or Postgres-as-queue) before Kafka specifically, since Kafka's partitioning and consumer-group machinery solves throughput/ordering/replay problems this system doesn't have at its actual scale.

03 Database design

Qs 45–74

46–51 Schema shape, tenancy, normalization

Core: institutions (tenants) → profiles (extends auth.users; carries role/institution_id/mentor_id/cohort_id) → teams/team_members (a startup can have multiple founders). Supporting tables: progress, meetings, evaluations, tasks, messages (mentor↔student), resources, documents+document_requests, achievements, community_messages, events+event_rsvps, announcements, applications, invitations, reports (JSONB blob per validation run), and a team_engagement view.

Where I intentionally denormalized: profiles.startup (plain text) was kept even after introducing teams as its own entity — the migration's own comment says why: existing dashboards still read it, and it's backfilled into teams rather than dropped, so nothing broke mid-migration. That's a conscious backward-compatibility tradeoff, not an oversight. Everywhere else, the schema is normalized to 3NF — a startup's funding/sector/stage live once on teams, not duplicated per founder.

52–65 Keys, indexes, scale

Primary keys / UUID vs auto-increment (52–53)Every table uses uuid primary key default gen_random_uuid(). Two reasons: the client sometimes needs the id immediately after insert without a round trip (e.g. creating a team, then inserting the founder's team_members row against that id in the same flow), and UUIDs are used directly as Storage path prefixes (${studentId}/...) and in RLS comparisons, where sequential IDs would be a minor enumeration risk.
Indexes (54–58)Explicit ones: invitations_email_idx on (lower(email)), hit on every signup; and a unique index on team_members(profile_id) that doubles as a business-rule enforcement — one person, one startup — as a side effect of being an index. Beyond that I rely on automatic PK/FK indexes; at this data volume I haven't needed to hand-tune plans.

100M rows / partitioning (59–61): honestly, this schema wasn't designed for that. The realistic path: the data is already naturally partitioned by institution_id on every table — that's the sharding key I'd reach for first, before jumping to physical sharding. The team_engagement view (live max()/count() aggregates across meetings/evaluations) would need to become a materialized view refreshed on a schedule.

66–74 Concurrency, transactions, consistency

I don't manage explicit transactions in application code — the risky multi-step writes are handled by Postgres triggers instead, atomic by construction: handle_new_user() (signup → invitation lookup → profile insert, all in one trigger function), set_institution() (stamps tenant on insert), and two guard triggers — guard_profile_columns() and guard_team_funding() — both running before update, so the check-then-block happens in the same statement as the write, no race window.

Concurrent updates (66–69): the clearest real case is a mentor and admin both editing a student's progress — handled with upsert(row, { onConflict: 'student_id' }), last-write-wins. I accepted that because progress updates are low-frequency and not financially sensitive. I would not accept last-write-wins on teams.funding_raised — that's exactly why it's separately trigger-guarded so only a mentor/admin can touch it at all, shrinking the concurrent-writer set to "staff," where a lost update is a Slack message away from being noticed, not a silent bug.

04 API design

Qs 75–97 — one custom endpoint, everything else is Supabase's auto-generated REST

Why POST for validate (78): not idempotent by nature — each call re-runs 10 LLM calls and can return different text — has a body, has side effects. Textbook POST.

Validation (81–83): minimal on the backend by design — IdeaRequest is a Java record with no @NotNull/@Valid. The frontend enforces required before submit. Real gap I'd flag proactively: a client bypassing the UI could send blank fields and burn an LLM call — I'd add @Valid + @NotBlank as the first fix.

Error handling (84–85): one global handler, ApiExceptionHandler, catches RestClientException (n8n unreachable/timeout/error) and returns a 502 with an actionable message ("Make sure n8n is running and the NEXUS workflow is Active") rather than a stack trace. There's no catch-all Exception handler, so any other bug still leaks Spring's default error page — another named gap.

Idempotency / retries (88–93): not handled for /validate — a double-click submits two full pipeline runs. Low real-world impact for a human founder submitting once; the honest fix is disable-on-submit (already a soft mitigation via the loading state) plus, if made async, an idempotency key.

Timeouts (94–95): explicit and deliberate — 10s connect / 180s read. Connect fails fast if n8n is unreachable; read stays generous because the pipeline legitimately takes up to 90s and cutting it off early would waste a run that would have succeeded.

Versioning (86–87): none — single unversioned /api prefix, frontend and backend deploy together. I'd move to /api/v1 the moment an external consumer needed the old contract preserved.

05 Authentication & security

Qs 98–120 — the strongest, most distinctive part of this project's design

99–108 Supabase JWT + RLS as the real authorization layer

Supabase Auth issues JWTs on signup/login (signUp / signInWithPassword / signInWithOAuth for Google). AuthProvider listens to onAuthStateChange, and on any session loads the matching row from public.profiles — so "the user" in the UI is always the profile, and role comes from the DB, never from client state.

Why JWT, not server sessions (100–101): not really a from-scratch choice — Supabase's model is JWT-based, and it's the right fit for a BaaS architecture where the browser talks to Postgres directly: the JWT is exactly what auth.uid() reads inside every RLS policy.

RBAC (109): enforced at two layers deliberately — ProtectedRoute.jsx gates routes client-side by user.role (UX-only, trivially bypassable), and Postgres RLS policies are the real gate — every table has explicit using/with check clauses keyed off auth.uid(), my_role(), my_institution(). Role is never trusted from the client.

The actual security storyThe original handle_new_user() copied role straight from client-supplied signup metadata — anyone with the public anon key could sign up as admin. The multi-tenant migration fixes this explicitly: self-signup is always student; elevated roles require a DB-side invitation row, matched by email, checked server-side in the trigger. Two guard triggers close the same class of bug elsewhere — guard_profile_columns() blocks a non-admin from changing their own role/institution_id/funding_raised; guard_team_funding() does the same for teams.funding_raised, since that field drives the public leaderboard.

111–120 Injection, XSS, CSRF, secrets

SQL injection: no hand-built SQL anywhere — all Supabase calls go through the parameterized JS client; the one place raw text reaches SQL-adjacent code is .ilike('name', name.trim()) in joinTeamByName, still parameterized.

XSS: React escapes all interpolated text by default; no dangerouslySetInnerHTML anywhere, so stored strings (chat messages, announcements) render as text, not HTML.

CSRF: mitigated structurally — the Supabase client uses bearer-token auth, not ambient cookies, so there's no cookie-based session for a forged cross-site request to ride on. The Spring endpoint has no session/cookie auth at all — it's origin-restricted via CorsConfig's allowedOrigins, not per-request authenticated. Real gap: a server-to-server call (not subject to CORS) could still hit /api/validate directly and burn Gemini quota — I'd add a shared-secret header or rate limiting if this were public-internet-facing at scale.

Secrets (118–120): .env.local holds the Supabase anon key — meant to be public by design (RLS protects the data, per the code's own comment), so committing it isn't the same class of leak as a service-role key. Still inconsistent with .env.example being left blank, worth cleaning up even though low-risk. Backend secrets (N8N_WEBHOOK_URL, CORS_ORIGINS) are injected per-deploy as environment variables, never hardcoded.

Passwords (115–116): never touched by my code — Supabase Auth hashes and stores them.

06 Scalability & caching

Qs 121–162 — honest scope: built for an incubator cohort, not internet scale

Current bottleneck (122–126): Gemini's free-tier rate limit, by a wide margin — the app's own infrastructure would comfortably outlast the AI provider's quota. Second: the single n8n instance on one host with no redundancy.

Statelessness (131–133): the Spring Boot backend is fully stateless — no session, no in-memory cache — so it scales horizontally trivially if ever needed. The frontend is a static SPA, infinitely horizontal by CDN nature. The one stateful piece is n8n's own execution history — that's the actual constraint, not my code.

At 10–100× traffic (139–143): (1) move validate to async so I'm not holding 180s connections open — the single highest-leverage change; (2) run n8n on a real Postgres backend with multiple workers instead of one SQLite-backed instance; (3) cache-aside the public showcase/leaderboard/scheme data (read on every dashboard load, tolerant of staleness); (4) Supabase's own Postgres tier scales independently until I outgrow their managed offering.

Redis — not used, but here's the specific plan if I added it (144–158): cache the showcase and leaderboard views — expensive-ish joins across teams/team_members/progress, read constantly, fine to be a few seconds stale. Cache-aside, short TTL (~60s), no invalidation logic needed. I would explicitly not cache anything RLS-protected behind a shared cache without keying it per-user — that's exactly the kind of design that leaks tenant data across institutions, which matters a lot given how much of this project's actual design already centers on strict institution isolation.

07 Kafka / message queues

Qs 163–191 — not part of this project

No event pipeline exists; the one place an async event conceptually belongs — idea submitted → report ready — is currently one long synchronous HTTP call. If I introduced a queue, that's exactly what it would replace: POST /api/validate publishes validation-requested and returns 202 with a report id immediately; a worker consumes it, calls n8n, writes the result back or publishes validation-failed with a retryable reason. I'd reach for a simple queue (SQS, or Postgres-as-queue) before Kafka — Kafka's partitioning and consumer-group machinery solves very-high-throughput, strict-ordering, replay problems this system doesn't have at its actual scale; it would be pure operational overhead here.

08 Concurrency & multithreading

Qs 192–210

No explicit multithreading code — Spring Boot's embedded Tomcat handles one thread per request by default. The only "concurrency" in my own code is the frontend's Promise.all() fan-out used throughout store.js and dashboard loaders (e.g. AdminDashboard's loadAll() firing 7 Supabase queries in parallel). No shared mutable state exists in the backend (stateless per request), so there's no realistic race condition to guard with locks in this codebase. The actual concurrency-correctness story lives in Postgres: before update guard triggers run inside the same transaction as the write they're checking, so there's no check-then-act race window.

10 "Design it for 10 million users"

Qs 232–251

I'd say this plainly: SIVP was designed for a specific, bounded audience — one or a handful of university incubators, each with dozens to low hundreds of founders — not internet scale. 10M users changes the problem, not just the numbers: at that scale I'm not running "an incubator platform," I'm running a multi-tenant SaaS, and the honest first move is re-examining whether one Supabase project is still the right foundation versus dedicated Postgres with read replicas, a real cache tier, and the async validation queue described in Section 6/7 as table stakes. I'd rather give that grounded answer than pretend to have already solved problems at a scale this project was never built for.

11 AI / LLM pipeline

Qs 252–280 — this is an LLM-heavy project, just orchestrated in n8n, not in my own backend

Why Gemini 2.5-flash (254–256): the free-tier constraint drove this directly — gemini-2.0-flash has 0 free-tier quota (a documented gotcha I hit), 2.5-flash doesn't, and Flash is cheap enough (fractions of a cent/call) to run 10 agents per validation without needing a bigger model.

Prompt architecture (257–258): each of the 10 agents is a fixed system prompt + a shared user-prompt template — the 7 idea fields, or upstream agents' JSON for agents that need context (FundIQ's prompt explicitly pastes in MarketMind.opportunityScore, RivalScope.competitionLevelScore, etc., so its weighted Investor Readiness Score is computed from real upstream numbers, not invented in isolation). Structured Output Parsers (JSON-schema-by-example) constrain each agent to a fixed shape.

Hallucination mitigation (259): every system prompt explicitly instructs the model to label estimates as estimates and never present invented figures as fact. normalizeReport.js adds a second defensive layer — e.g. it never invents a 5-year revenue curve from FundIQ's prose forecast; if the model didn't return a numeric series, the chart is skipped and the text is shown as-is instead of fabricating data points.

Rate limits/timeouts (269–270): handled at two levels — n8n's "Retry On Fail" for transient 503s, and Spring Boot's 180s read timeout as the outer bound.

Caching LLM responses (272–273): not done, and I wouldn't — each response should reflect that specific founder's specific idea; the only thing that functions as a de facto cache/fallback is the static SAMPLE_REPORT shown before a live report exists.

12 RAG

Qs 281–306 — not part of this project

No retrieval or embedding pipeline. Every agent reasons from the 7 submitted idea fields plus upstream agent JSON and the model's own training knowledge, which is exactly why every prompt is careful to say "label as estimate" rather than claim grounded facts. If I added RAG, the obvious candidate is MentorAI — grounding government-scheme recommendations in an actual up-to-date scheme database, since the static SCHEMES list I maintain by hand is exactly the kind of source that goes stale and is a natural embeddings-index candidate, instead of relying on model training data that can be outdated on eligibility rules.

13 Voice AI / calling

Qs 307–331 — not part of this project

No telephony or voice pipeline anywhere in this codebase — there is no analog worth stretching for here.

14 Observability & testing

Qs 332–362

Observability: minimal today — console logging only (missing-env-var errors, and the raw pipeline response is logged to the browser console on every validation so its exact shape is inspectable). No structured backend logging, metrics, or tracing. First thing I'd add: structured logging around the n8n call specifically — request id, latency, outcome — since that's currently the one place failures are invisible except as a 502 in the browser.

Testing: the only test dependency present is spring-boot-starter-test in pom.xml — no test files exist in the repo. I'd say that plainly rather than claim coverage I don't have. Highest-value tests if scoped: N8nService with a mocked RestTemplate (timeout/error paths), and the Postgres trigger functions (guard_profile_columns, guard_team_funding, handle_new_user) since those encode the actual security invariants.

15 Deployment / DevOps

Qs 363–377

Two deploy paths exist in the repo, reflecting a real migration in progress. The original: Vercel (frontend) + Render (backend, via render.yaml) + n8n hosted/tunnelled separately, documented in DEPLOYMENT.md. The current production target: a single EC2 host running nginx (TLS termination + static frontend + a same-origin /api/ reverse proxy, which removes CORS from the picture entirely) alongside the Spring Boot backend and n8n, all as Docker Compose services.

push to main→ CI builds & tags image by commit SHA→ docker compose pull/up on the host

Images are tagged by commit SHA, never :latest, so docker compose up reliably recreates containers on every deploy. Every service caps its own logs (max-size: 10m) so the disk doesn't silently fill. n8n's execution history is explicitly pruned (7-day / 2000-execution caps) for the same reason — one validation writes 11 executions, each holding the full JSON payload passed downstream, and that grows without bound otherwise.

Migrations: the Supabase SQL files (schema.sql, then additive migrations) are applied manually through the SQL editor — no Flyway/Liquibase-equivalent tooling. Honest gap; I'd track these as versioned migrations the moment more than one person needed to apply them consistently.

Zero-downtime / rollback: not implemented — a single-host Compose deploy briefly cycles containers. The real fix is the same as any monolith: multiple backend instances behind a load balancer, deploy to one, health-check, cut over.

16 The "why → why not" drill, worked example

The recurring depth pattern, worked through with SIVP's real timeout design

Why a 180s read timeout on the n8n call? The 10-agent pipeline legitimately takes 30–90s (10 sequential/parallel LLM calls), and cutting the connection off early would waste a run that would have succeeded.

Why not just poll instead of one long synchronous call? Simplicity for the current traffic profile — a founder submitting once and waiting is acceptable UX at this scale, and async polling was explicitly deferred as a later-phase item rather than skipped by accident.

What's the actual risk of the synchronous approach? A held-open HTTP connection for up to 180s per validation ties up a request thread the whole time, and a page refresh mid-run loses all state with no resume path.

What happens if n8n hangs past 180s? RestTemplate throws, ApiExceptionHandler catches it, the founder sees a clean 502 with an actionable message instead of an infinite spinner.

What happens at 10× concurrent validations? Nothing in my own stateless backend breaks — it just means more concurrent threads held open for up to 180s each. The real ceiling is Gemini's own rate limit, hit long before Spring Boot's thread pool would be.

What would you change first? Make it async: return a report id immediately, let the frontend poll or subscribe, freeing the backend from holding long connections and giving me a natural retry point if n8n times out.

The pattern to reuse on any other component: what → why → alternative rejected and why → tradeoff accepted → failure mode → behavior at 10× → the one thing you'd change first. Run this same chain for the RLS-as-authorization design and for the CRUD-direct-to-Supabase vs. AI-through-backend split — those are the two most likely to get drilled here.

17 The dangerous ones

One-line answers, ready to expand from any section above

  • Architecture: stateless Spring Boot bridge + browser-direct Supabase for CRUD, split by latency profile (ms vs. 30–90s), not by team boundary.
  • Database: Postgres via Supabase — the data is relational and RLS gives me real multi-tenant authorization for free.
  • Why not X: microservices, Kafka, Redis, GraphQL, gRPC all solve problems this system doesn't have at its actual scale — a cohort of founders, not internet traffic.
  • n8n down: every validation 502s with a clean message; everything else (dashboards, chat, docs) keeps working since nothing else depends on it.
  • Biggest bottleneck: Gemini's own free-tier rate limit, not my infrastructure.
  • How to scale: make validation async first (highest leverage), then cache the public read-heavy views, then a real Postgres-backed n8n with multiple workers.
  • Concurrent same-data edit: last-write-wins on progress (low-stakes); guard triggers instead of locking on funding_raised (high-stakes, narrowed to a trusted writer set).
  • Security's real story: role is never trusted from the client — RLS + guard triggers enforce role/institution/funding changes server-side, closing a documented self-escalation bug from an earlier version.
  • Failure handling: one global exception handler turning n8n failures into a clean 502; no retry/circuit breaker yet — named gap.
  • Caching: none today; if added, cache-aside on the public showcase/leaderboard only — never on anything RLS-protected without per-user keying.
  • Kafka: not used — no event-driven feature exists yet to justify it.
  • Sync vs async: everything synchronous today; validation is the one place I'd deliberately make async first.
  • Redesign for production: async validation queue, per-agent fallback in NEXUS, structured backend logging, migration tooling for the SQL schema, request validation on IdeaRequest.
  • Weakest part: the single self-hosted n8n instance with no redundancy — said plainly, not hidden.
  • Hardest problem solved: writing normalizeReport.js to defensively tolerate a non-deterministic LLM pipeline's raw JSON — unresolved template expressions, trailing-space keys, inconsistent currency formatting — without ever inventing data the model didn't actually return.
  • A decision you'd revisit: making the validate flow synchronous from day one instead of async from the start — reasonable for the MVP, but the first thing I'd unwind.
